# 这个形状是怎么试出来的

实测环境:Claude Desktop,claude-code 2.1.234 / 2.1.237,macOS。2026-08-20 ~ 08-24。
下面每条都是撞出来的。改 `watch-loop.sh` 或想换一种调度方式之前先读这里。

**这些都是对某个版本的观察,不是稳定接口。** 换个版本可能就变了 —— 真要依赖,自己重测一遍。

## 成立的机制:background shell + exit

Bash 工具的 `run_in_background: true` 把命令 detach 出去。实测:

| 观察 | 数据 |
|---|---|
| 跨轮次存活 | 探针跑满 240s、16 拍不差,期间跨过了轮次边界 |
| 退出能唤醒 agent | `exit 7` → harness 通知 `failed with exit code 7`,agent 被重新调用 |
| 被 kill 也唤醒 | `pkill` 掉,`exit 144`(128+SIGTERM)照样有通知 |
| 长命 | 另一个探针连续心跳无断层,没有被限速或收割 |
| 只回本会话 | 输出目录是 `/private/tmp/claude-$UID/<project>/<session-id>/tasks/`,按会话隔离 |
| 继承钥匙串 | `gh`(token 存 keyring)在后台进程里正常工作 |
| 可并行 | 5 个同时跑,独立 pid / 锁 / 状态,5 条通知一条不丢 |

没找到定期收割 background shell 的机制。但**app 退出会带走它们** —— 它是 claude 进程的
子进程。这是这个方案唯一的耐久性缺口。

对比:`nohup` 起的进程更耐久(实测活了 3 天),但它**没有办法唤醒 agent**,只能写文件等人
来读。所以 nohup 适合纯采集,不适合盯守。

## 走不通的路 1:系统 cron

**症状**:`gh api` 在 cron 里返回 `Not Found (HTTP 404)`,同样的命令手跑成功。

**原因**:`gh` 的 token 存在 keyring。cron 跑在另一个 bootstrap namespace,读不到登录
钥匙串,于是发出未认证请求 —— 私有 repo 对未认证请求返回 404 而不是 401,所以日志上
看起来像路径写错了。

证据链:

| 观察 | 说明 |
|---|---|
| `gh auth status` 显示 `(keyring)` | token 在钥匙串,不在文件里 |
| GUI 会话里同一个调用成功 | 路径和权限都没问题 |
| cron 里 404 ×3 | 请求发出去了但没带有效凭证 |
| 完全无配置时 `gh` 是**拒绝执行**、不是 404 | 排除「配置丢了」这个解释 |

顺带另一个必踩的:cron 的默认 PATH 是 `/usr/gnu/bin:/usr/local/bin:/bin:/usr/bin:.`,
homebrew 装的东西全都找不到。

## 走不通的路 2:操纵 app 自己的定时任务

思路是:agent 自己排一个定时 task,然后让 shell 在外面改这个 task 的触发时间 —— 没事就
往后推,有事就让它响。这样空转完全不唤醒 agent。

**这条路的前 90% 都成立,最后一步塌了。**

从 shell 删掉或改期一个待触发的 task **确实生效** —— 但只在 agent 处于**活动轮次内**改
文件时生效。agent 空闲之后改文件一律无效,而 guard 要干活的时刻,恰好就是 agent 空闲的
时候。那个任务文件不在 app 的文件监听范围内,只在会话有活动时才重读。

现场数据:

```
12:20:18  推到 12:25
12:22:21  推到 12:27
12:24:24  推到 12:29      ← 这行之前 agent 结束了一轮对话
12:26:28  推到 12:31
实际触发: 12:27           ← 用的是 12:22:21 那次写进去的值
```

**当初为什么没发现**:七个探针全都是在一轮对话之内改完文件、然后才结束那一轮,所以每次
都赶在重读之前,看着都对。测试条件设窄了。

还有一个反直觉的点:定时任务是由**持有调度锁的那个会话**执行的,不是创建它的那个。同一
个目录下开着多个会话时,任务可能在另一个会话里响,而且锁会易主。所以这类机制做不到
「定向唤醒某个会话」。`run_in_background` 的输出目录直接按 session id 隔离,没有这个问题。

## 一条被推翻的推断

中途我判断「desktop 每轮新建 claude-code 进程」,并据此排除了某种可能。进程这部分是错的
—— 2.1.237 里父进程跨轮次存活。结论没变,但依据不成立。记在这里是因为:**这类机制没有
文档,全靠观察,而观察很容易在一个没意识到的条件下做出来。** 上面「路 2」塌掉也是同一个
病 —— 七个探针共享了同一个未言明的前提。

## 成本模型

一次唤醒的地板价是整个会话上下文的 cache read。所以:

- 会话越大,每次唤醒越贵。长盯的 watch 放在一个专用的小会话里会便宜得多
- 唤醒时进上下文的 tool 输出**永久留着**,后面每轮唤醒都要重新 cache-read。这是复利式
  膨胀,也是为什么 probe 必须在 shell 里把数据压成摘要
- 睡眠本身不花钱。所以轮询密度可以放得比直觉更高(CI 用 30s 完全没问题),真正要省的
  是唤醒次数和每次唤醒带进来的字节数

## dead-man 特性

循环意外死掉 → 它退出 → agent 被唤醒。静默失效是盯守类工具最难查的问题,而这个形状
天然带告警。实测撞到过一次:probe 因为认证问题挂了,agent 醒来发现循环死了。

唯一不告警的失效方式是**probe 挂死**(比如 `curl` 没设超时)。所以 probe 里所有网络调用
都要有超时。同理,probe 里多个子请求的退出码要逐个检查 —— 拿到半截数据却当成功返回,
游标照推,丢掉的那条就再也不会出现了。
